# MyGym у Google Play: дослідження переносу на React Native

> Дослідження від 2026-10-20, вичищене 2026-10-22 від того, що вже зроблено або
> не справдилось (HTTPS, `/privacy`, гіпотеза про каскадне видалення, «Google-входу
> нема»). Конкретні зміни бекенду й вебу — у завданнях `01–09` цієї папки; тут —
> контекст, вибір стеку для мобільного застосунку, план і вимоги Google Play.
> Версії бібліотек і дати — станом на жовтень 2026, перед стартом перевірити.

## Коротко

Перенести MyGym на React Native реально, і в коді особливих ризиків немає. Розумний
вибір — Expo (SDK 57, згодом 58) з Expo Router, NativeWind і тим самим TanStack Query.
Окремим пакетом у монорепо можна винести приблизно **третину фронтенд-коду за рядками**
(API-шар, типи, утиліти, словники i18n); сторінки й компоненти доведеться переписати на
RN-примітивах, а Recharts замінити на victory-native.

Терміни визначає не написання коду, а процедура Google. Особистий акаунт, створений
після 13.11.2023, має пройти **закритий тест із ≥12 тестерами протягом 14 днів поспіль**,
потім Google до 7 днів розглядає заявку на production і ще до 7+ днів робить рев'ю
релізу. Тому план побудований так, щоб закритий тест почався якомога раніше, на
застосунку, яким уже можна реально логувати тренування. Оцінка (не опублікована
метрика): **9–12 тижнів part-time** від старту до публічного релізу, з них 5–8 тижнів
чистої розробки.

## Що переноситься, а що ні

За кількістю файлів фронтенд майже платформонезалежний: більшість файлів у
`frontend/src` — чистий TypeScript без DOM (`shared/api/**` з axios-викликами,
`query-key-factory` і хуками, `types/`, утиліти `progressionMessage`, `labelColor`,
`apiError`, `weight`, словники `en/uk.json`). За рядками картина інша: сторінки й
компоненти — приблизно дві третини коду, і вони на DOM і Tailwind. Саме там живе
найцінніше: автозбереження з послідовним `flushSave`, меню шаблонів і програм,
календар консистентності.

Звідси порядок: **спершу винести бізнес-логіку зі сторінок у хуки й чисті функції**
(завдання 6), потім переписувати UI. Інакше чергу строго послідовних збережень доведеться
копіювати руками, а це найпростіший спосіб повернути баг із дублюванням підходів
(`PUT /api/workouts/:id/exercises` перезаписує всі вправи тренування).

`api/client.ts` уже має правильну логіку (single-flight refresh, оновлення за 60 с до
`exp`, реакція на повернення у вкладку), але прив'язаний до браузера: `import.meta.env`,
відносний `/api`, `withCredentials`, `atob()`, слухачі `document`/`window`. На RN
`visibilitychange` стає `AppState` 'active', `online` — слухачем NetInfo, логіка та сама
(завдання 7). `i18n/index.ts` на мобільному: замість браузерного детектора й
`localStorage` — `expo-localization` + AsyncStorage (не перевірено).

Повністю веб-специфічне: `react-dom`, `react-router-dom`, `recharts`, `tailwindcss`,
детектор мови, devtools, `document.addEventListener` для click-outside/escape,
`<input type="date">`, `FormData` з `File` у CSV-імпорті.

Бекенд для мобільного клієнта майже готовий: захищені ендпоінти вимагають
`Authorization: Bearer`, а не cookie (`plugins/authenticate.ts`), коди помилок стабільні
й i18n-дружні (`translateApiError` переноситься як є), CORS для нативного застосунку
значення не має. Чого ще бракує — завдання 2 (refresh у JSON), 3 (видалення акаунта),
4 (сторінка видалення), 5 (мінімальна версія клієнта). Мобільному клієнту потрібен
абсолютний base URL (`https://<домен>/api`) — тримати його в конфігурації збірки.

## Стек мобільного застосунку

**Expo з CNG, а не bare React Native CLI.** Офіційна документація React Native радить
починати нові застосунки з фреймворку і називає Expo; розробку без фреймворку описує як
варіант для «unusual constraints» ([reactnative.dev](https://reactnative.dev/docs/environment-setup)).
Для MyGym відмова від Expo нічого не дає: secure storage, нотифікації, keep-awake,
haptics, локалізація, вибір файлу мають готові Expo-модулі. Continuous Native Generation
(`android/` генерується, а не редагується руками) знімає більшість болю з оновленнями;
у SDK 57 `expo prebuild` за замовчуванням перегенеровує нативні папки
([Expo SDK 57](https://expo.dev/changelog/sdk-57)). Ціна — будь-яку нативну зміну
оформлювати як config plugin; для застосунку без власного нативного коду вона теоретична.

**Версія.** На 20.10.2026 найновіша — **SDK 58** (RN 0.88, React 19.3), але Expo Go для
неї ще не було в сторах, а `create-expo-app` генерував **SDK 57** (RN 0.86, React 19.2)
([Expo SDK 58](https://expo.dev/changelog/sdk-58)). Рекомендація: стартувати на 57,
перейти на 58, коли бібліотеки наздоженуть, але **не посеред закритого тесту**. 55/56
обійти через регресію пам'яті Hermes v1 з Reanimated, виправлену в 57. SDK 56–58 мають
**targetSdk 36** — саме цього Google Play вимагає від нових застосунків з 31.08.2026
([Android target SDK](https://developer.android.com/google/play/requirements/target-sdk)).

**Навігація: Expo Router.** File-based routing: `/workouts/:id` стає
`app/workouts/[id].tsx`, deep links безкоштовно. З SDK 56 Expo Router не залежить від
react-navigation, у SDK 58 стабілізовано native tabs і toolbars; старі туторіали з API
React Navigation часто вже не застосовні — довіряти документації Expo. Пагінацію журналу
(`?page=N`) на мобільному замінити нескінченним списком (`useInfiniteQuery` + `FlatList`).

**Стилі: NativeWind v4.** Tailwind-рефлекси й сотні `className` у поточному коді роблять
його найдешевшим входом; утиліти компілюються на етапі збірки. Класи не копіюються один в
один: у RN нема каскаду, `hover:` чи grid. Альтернативи: Unistyles 3 (швидший, але
StyleSheet-API — навички Tailwind не переносяться), Tamagui (крута крива навчання,
окуповується лише при спільному UI з вебом, якого не пропонується).
**Перевірити:** чи вийшла стабільна NativeWind v5 і чи працює v4 з Tailwind 3.4 (веб зараз
на ньому) — тоді конфіг і палітру можна ділити між вебом і мобільним.

**Дані: TanStack Query лишається, офлайн у два рівні.** Конвенція `shared/api/<ресурс>/`
переноситься без змін. Погана мережа в залі вже була проблемою на вебі (звідси
grace-вікно ротації 60 с).
- Рівень 1: персистенція кешу (persister + MMKV або AsyncStorage) і пауза мутацій офлайн
  через `onlineManager` + NetInfo — збереження підходів переживе навіть перезапуск.
  `PUT /:id/exercises` — ідемпотентна повна заміна, тож черга «зберігай лише останній
  стан на тренування», без sync-движка.
- Рівень 2 — лише якщо треба *створювати* тренування без мережі: `expo-sqlite` (Drizzle
  його підтримує) + outbox; клієнт генерує UUID сам, `POST /api/workouts` має їх приймати.
  WatermelonDB для кількох тисяч рядків надлишковий; Realm не брати (депрекейт Atlas
  Device Sync у 2024).
- **Перевірити:** актуальний API `PersistQueryClientProvider`/`resumePausedMutations`
  у TanStack Query v5 на RN і версію `react-native-mmkv`.

**Графіки.** Recharts лише для DOM: `ProgressChart` (лінія, точки рекордів, тултип) і
`WeeklyCategoryChart` (згрупований bar) переписати. Найближчий аналог —
**victory-native 41.x (Victory Native XL)** на `@shopify/react-native-skia`
([GitHub](https://github.com/FormidableLabs/victory-native-xl)); простіша альтернатива —
`react-native-gifted-charts`. Спільна лише підготовка даних (`HistoryPoint`).

**Нативні можливості.**
- Таймер відпочинку: JS-таймер у фоні не запускати. Зберігати час завершення, на resume
  рахувати залишок, планувати локальну нотифікацію `expo-notifications` з тригером
  `TIME_INTERVAL`. Спершу створити notification channel (на Android 13+ без каналу запит
  дозволу не з'явиться). Точний час вимагає `SCHEDULE_EXACT_ALARM`, а Android 14+ за
  замовчуванням його новим застосункам не дає — неточного тригера + відліку на екрані
  (`expo-keep-awake`) достатньо.
- Нагадування в дні тренувань (`users.trainingDays` уже є) — природний наступний крок.
- Health Connect і віджет (`expo-widgets`, Android з SDK 58) — після релізу: Health
  Connect тягне окрему декларацію і рев'ю.

**Вхід через Google на мобільному.** У вебі він уже є (серверний flow з редиректом і
cookie), мобільному потрібен свій шлях — рішення в завданні 2, пункт 7. Бібліотеки:
безкоштовна «Original» `@react-native-google-signin` побудована на legacy SDK, який Google
«may remove from Play Services»; безпечніше — `react-native-nitro-google-signin` з
Credential Manager. Платна Universal-версія офіційно підтримує Expo лише до SDK 57
([react-native-google-signin](https://react-native-google-signin.github.io/docs/install),
[Expo Google auth](https://docs.expo.dev/guides/google-authentication/)).

**Структура: pnpm-монорепо, UI не спільний.** `apps/web` (Vite без змін), `apps/mobile`
(Expo), `apps/backend`, `packages/shared` (типи + Zod-схеми — можна поступово підняти з
бекенду як єдине джерело валідації), `packages/api` (клієнт, ключі, хуки),
`packages/i18n` (словники + `progressionMessage`, `labelColor`, `weight`). Expo підтримує
pnpm workspaces нативно ([Expo monorepos](https://docs.expo.dev/guides/monorepos/)).
Головна пастка — **дублікати React**: SDK 57 пінить React 19.2, веб на 18.3. Рішення —
оновити веб до 19 (завдання 8) або React у `packages/*` лише як `peerDependency`.
Сховище токена — через інтерфейс `TokenStore` (завдання 7). Один Expo-кодбейс і для вебу
свідомо не рекомендується: переписати робочий Vite-застосунок без користі для Play.

**Збірки, тести, моніторинг.** Безкоштовний EAS: **15 Android-збірок на місяць**, 1 000 MAU
для EAS Update, низький пріоритет черги, таймаут 45 хв ([expo.dev/pricing](https://expo.dev/pricing));
`eas build --local` або Gradle після prebuild обходять ліміт. EAS Update — OTA-фікси JS
без рев'ю в сторі. Тести: Jest + `jest-expo` + React Native Testing Library, e2e — Maestro,
креші — Sentry. CI: окрема джоба для мобільного (typecheck + тести пакетів; EAS Build за тегом).

**Дрібне на пам'ять.** Rate limit 10 логінів/хв і 5 реєстрацій/15 хв на IP може
зачепити мобільних користувачів за CGNAT оператора — на старті не проблема.

## План: критичний шлях іде через календар Google

Обов'язкові кроки для нового особистого акаунта: реєстрація за **$25 одноразово**
(верифікація ID, телефону, email і реального Android-пристрою через застосунок Play
Console, [Help](https://support.google.com/googleplay/android-developer/answer/10841920?hl=en)),
перше рев'ю релізу в закритому треку, **14 днів закритого тесту з ≥12 тестерами без
перерви** ([Help](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en)),
заявка на production («зазвичай до 7 днів») і рев'ю production-релізу («up to 7 days or
longer», для нових акаунтів довше, [Help](https://support.google.com/googleplay/android-developer/answer/9859751?hl=en)).
Від готового закритого білда — **щонайменше 3–4 тижні** процедур.

Головна думка: **закритий тест стартує на «мінімально корисному» білді, а не на
фінальному** — логін, журнал, запис тренування з автозбереженням, вправи, програми. За
повідомленнями спільноти (не документація Google), нові білди й нові тестери лічильник
14 днів не скидають, а пауза треку скидає; Google дивиться на реальну активність
([TestersCommunity](https://www.testerscommunity.com/blog/google-play-closed-testing-requirements-2026)).
Тестери мають справді логувати тренування кілька разів на тиждень.

| Фаза | Тижні (оцінка) | Що робиться | Чому саме тут |
|---|---|---|---|
| 0. Фундамент | 1–2 | Завдання 2–5 (refresh у JSON, видалення акаунта, сторінка видалення, мінімальна версія клієнта). **Паралельно:** зареєструвати Play Console і почати збирати ~15 тестерів. | Блокує перший білд для тестерів; реєстрація акаунта має власний невідомий лаг |
| 1. Монорепо і каркас | 1–2 | Завдання 6–9 (хуки, `TokenStore`, React 19, тести фронтенду), pnpm workspaces, винесення `packages/*`. Expo SDK 57 + Expo Router + NativeWind, екрани логіну й реєстрації, SecureStore. | Рефакторинг вебу першим перевіряє, що спільні пакети працюють, поки ризик малий |
| 2. Ядро для тестерів | 2–3 | Журнал (infinite list), форма тренування з автозбереженням і офлайн-рівнем 1, вправи + дні тренувань, програми, меню нового тренування, профіль з видаленням акаунта, перемикач мови. Іконки з SVG «Сходинки» (adaptive icon), перевірка targetSdk 36 і 16 KB. | Мінімум, з яким тестери реально тренуються, + усе, що Google перевіряє вже на закритому треку |
| 3. Закритий тест (14+ днів) | 2–3 | Білд у closed track, ≥12 (краще 15) тестерів, opt-in. **Паралельно:** графіки прогресу (victory-native), календар консистентності, таймер відпочинку, store listing, скріншоти uk/en, Data safety, Health declaration. Фікси — нові білди або EAS Update. | Лічильник іде незалежно від розробки, другорядні екрани дописуються всередині тесту |
| 4. Production | 1–2 | Apply for production (розгорнуті відповіді — «тонкі» є частою причиною відмови), рев'ю, staged rollout | Не стиснути — залежить від Google |

CSV-імпорт свідомо поза першим релізом: це одноразова міграція з Google Таблиць, лишається
у вебі. Якщо знадобиться на мобільному — `expo-document-picker` + адаптація `FormData`.

**Акаунт організації** змінює критичний шлях: вимога про 12 тестерів — лише для особистих
акаунтів. Але особистий акаунт **публічно показує ім'я та адресу** розробника в лістингу;
організації потрібні D-U-N-S, верифікований публічний телефон і сайт. Чи може ФОП
зареєструватися як організація і скільки займає D-U-N-S в Україні — джерел не знайдено.
Питання адреси в публічному лістингу варто зважити свідомо.

## Ризики

| Ризик | Імовірність і вплив | Що робити |
|---|---|---|
| Тестери «відвалюються» або не активні, Google просить більше тестування | Середня, +1–3 тижні | 15 тестерів замість 12, реальні люди з залу, нагадування |
| Перше рев'ю нового акаунта затягується | Середня, +1 тиждень | Заповнити всі декларації до першого білда в closed track |
| Конфлікт React 18 (веб) і 19.x (Expo) у монорепо | Висока ймовірність, середній вплив | Завдання 8 або React як `peerDependency`; виявляти через `pnpm why` |
| NativeWind v5 / сумісність з Tailwind 3 не підтверджено | Середня | Перевірити GitHub-релізи NativeWind перед фазою 1 |
| Суперечливі дати 16 KB | Низька при сучасному Expo | Перевірка AAB, Play Console сама попередить |
| Перехід SDK 57 → 58 посеред закритого тесту | Низька | Мігрувати після production |
| Регресії автозбереження після рефакторингу в хуки | Середня, високий вплив (дублі підходів) | Юніт-тести черги збережень (завдання 9) |

## Відкриті питання (вирішує користувач)

- Чи потрібен офлайн-рівень 2 (створення тренувань без мережі), чи достатньо черги для
  вже відкритого тренування?
- Особистий акаунт розробника з публічною адресою чи шлях через організацію?
- Лишатися на DuckDNS чи переходити на власний домен до першої мобільної збірки
  (див. `01-https-domain.md`)?
- Як саме робити вхід через Google на мобільному (завдання 2, пункт 7) і чи потрібен він
  у першому релізі?
- Чи переносити CSV-імпорт на мобільний?
- Чи планується монетизація. Якщо так, цифрові фічі в застосунку — лише через Play Billing:
  15% на перший $1M для стандартних ринків; для користувачів з ЄЕЗ/UK/US з 30.06.2026 —
  нова структура 10% + 5% на підписки ([Help](https://support.google.com/googleplay/android-developer/answer/112622?hl=en)).
  Як регіон користувача застосовується до українського розробника — уточнити.

## Висновок

React Native — найпередбачуваніша частина: порт — переважно механічний переклад JSX під
інші примітиви поверх уже правильно розшарованого коду, а конвенція `shared/api` по суті
вже готовий спільний пакет. Справжня робота — довести бекенд до рівня «публічний продукт»
(завдання 2–5), і вона робить безпечнішою вже й веб-версію.

14-денний закритий тест перетворює реліз на задачу планування, а не швидкості: запускати
лічильник рано з корисним мінімумом і дописувати графіки, календар і таймер уже під час
тесту. Найдорожча помилка — випустити перший білд до тестерів без механізму мінімальної
версії клієнта (завдання 5): заднім числом його не додати.
