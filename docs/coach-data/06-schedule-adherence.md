# Завдання 6: Дотримання розкладу і пропуски — на бекенді

## Мета
Бекенд сам рахує, скільки тренувань планувалось і скільки зроблено за тиждень,
і віддає дати пропусків — тренеру через MCP, без здогадок за вереснем.

## Що вже є (не переробляти)
- `users.trainingDays` (ISO-дні, default `[1,3,5]`), `GET/PATCH /api/settings`,
  форма розкладу на сторінці «Вправи».
- `training_schedule_history` — розклад, що діяв на кожну дату.
- `ConsistencyCalendar.tsx` + `scheduleOn()` на фронтенді: стани
  `trained_planned / trained_extra / missed_planned / rest`, сьогодні нейтральне.
- Задача `docs/mobile-prep/06-extract-workout-autosave-hook.md` теж зачіпає
  `scheduleOn()` — узгодити, щоб логіка не роздвоїлась.

## Чого бракує
Уся логіка пропусків — лише на фронтенді; MCP її не бачить. Нема правила
«тренування в інший день того самого тижня зараховується замість пропущеного».

## Що зробити

### Бекенд
1. Перенести `scheduleOn()` у бекенд як чисту функцію (спільний алгоритм —
   пояснити, як не розійтись із фронтендом: або фронт починає брати готовий
   результат з API, або спільний пакет; рекомендовано перше).
2. `computeAdherence(workoutDates, scheduleHistory, breaks?, tz, from, to)` →
   по ISO-тижнях: `expected` (кількість планових днів тижня за розкладом, що
   діяв), `done` (дні з тренуванням `status <> 'abandoned'`, лише основні
   програми — обговорити, чи рахувати «прес + підтягування» повноцінним
   тренуванням), `missed[]` (планові дні без тренування, **але** компенсовані,
   якщо в тому самому тижні було тренування в неплановий день), `atRisk` для
   поточного тижня (днів лишилось менше, ніж бракує тренувань). `missed`
   фіксується лише після закриття тижня. Метрики: `adherenceWeek`,
   `adherence4w`, `weeklyStreak`, `currentGapDays`. Юніт-тести.
3. `GET /api/settings/adherence?from&to` — для календаря й головної.
4. `coach/summary` додає `adherence: { planned, completed, missed,
   longestGapDays, missedDetail: [{ date, planned: <програма за ротацією>, reason }] }`
   (`reason` з'явиться в завданні 7; поки `null`).
5. Перевірка на реальних даних: розклад пн/ср/пт, 8–21.10 → пропуски 14.10 і 19.10.

### Опційно (узгодити з користувачем)
6. Режим «N разів на тиждень» замість конкретних днів: `users.sessionsPerWeek`
   (nullable; якщо задано — `expected = N`, дні лише як орієнтир для календаря).

### MCP
7. Через `get_training_summary`; окремий `get_training_frequency` не потрібен.

### Фронтенд
8. Картка тижня на журналі: «Цього тижня: 2 з 3 · ще одне — і тиждень виконано»
   і «Сьогодні за планом: А» (з `GET /api/programs/suggestion`).
9. Календар: пропуски — нейтральним контуром, не червоним (зараз червоний —
   змінити за рішенням користувача); компенсовані тижнем — «виконано».
   Формулювання без докорів.
10. en/uk.

## Критерії готовності
- Календар і `coach/summary` дають однакові пропуски на тих самих даних.
- CLAUDE.md: правило компенсації в межах тижня, де живе логіка.
