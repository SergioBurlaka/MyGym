# Функції MyGym для аналізу тренувань: план реалізації

Десять функцій, які дають тренерові в Claude дані для аналізу, згруповані у три пріоритети й ідуть у тому самому порядку 1–10, що й у плані. Кожен пункт має однакову структуру: **мета → кроки (БД → API/MCP → UI) → готово, коли**. Назви таблиць і колонок у SQL умовні: підлаштуй їх під наявну схему MyGym (`Workout.timeStart/timeEnd`, `WorkoutExercise`, `Set` тощо).

| Пріоритет | Пункти | Результат для тренера |
|---|---|---|
| **A. Обов'язково** | 1 RIR · 2 Компактна історія · 3 М'язи · 4 Завершення тренування | Чисті, завершені сесії з близькістю до відмови; історія вміщується в контекст |
| **B. Дуже бажано** | 5 Тижневий обсяг · 6 Графік і пропуски · 7 Причина пропуску й нотатка | Обсяг на м'яз, дотримання плану, контекст перерв без ручних підрахунків |
| **C. Пізніше** | 8 Анкета готовності · 9 Годинник і ваги · 10 Біль і травми | Стан людини перед тренуванням і сигнали безпеки |

Пункти 1–4 зручно робити однією міграцією й однією гілкою: нові nullable-колонки в PostgreSQL додаються без перезапису таблиці ([PostgreSQL ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html)). Пункт 10 технічно незалежний і за потреби його можна підняти вище: він закриває найризиковіше місце, болі в плечах.

# A. Обов'язково

## 1. RIR на кожен підхід

**Мета.** Тренер відрізняє «9 легко» від «9 через силу» і вирішує, чи додавати вагу.

**Твоя ідея (радіокнопки 1–5 з поясненням у дужках)** правильна за суттю: саме RIR, а не RPE, мала шкала, пояснення людською мовою. Але є чотири зміни:

1. **Додати 0.** RIR 0 — це відмова, найважливіше значення. Без нього тренер не відрізнить «ще один повтор» від «до відмови» ([шкала Zourdos](https://openrepository.aut.ac.nz/items/efef3b25-6701-4fb5-bb82-55fcd2a26027/full)).
2. **Верх — «5+», а не 5.** При прогнозі «3 в запасі» люди помиляються на 3–5 повторів, тож 4, 5 і 6 — фальшива точність ([Casanova 2025](https://www.rdpc.uevora.pt/rdpc/bitstream/10174/39787/1/2025%20Casanova%20et%20al.%20Accuracy%20in%20predicting%20repetitions%20in%20reserve%20during%20resistance%20training.pdf)).
3. **Горизонтальний рядок замість вертикального списку.** Шість рядків тексту на кожен із ~20 підходів — це прокручування між підходами.
4. **Необов'язково й заповнено наперед.** Так роблять Hevy, Boostcamp і Alpha Progression: поле не блокує «підхід виконано».

**Кроки.**

1. **БД:**
   ```sql
   ALTER TABLE workout_set
     ADD COLUMN set_type   text NOT NULL DEFAULT 'normal'
         CHECK (set_type IN ('warmup','normal','dropset','failure')),
     ADD COLUMN rir        smallint CHECK (rir BETWEEN 0 AND 5),  -- 5 = «5+», NULL = не оцінено
     ADD COLUMN rir_target smallint CHECK (rir_target BETWEEN 0 AND 5),
     ADD COLUMN rir_source text CHECK (rir_source IN ('user','prefill')),
     ADD COLUMN logged_at  timestamptz;
   ALTER TABLE workout_set ALTER COLUMN logged_at SET DEFAULT now();
   ```
   `logged_at` спершу без default, щоб старі рядки лишились NULL, а не отримали час міграції.
2. **Ціль RIR у програмі:** колонка `rir_target` на вправі програми; за замовчуванням 1–3 для `large`, 0–2 для `small`.
3. **MCP — безпечний запис замість `log_workout_exercises`.** Новий `log_sets(workout_id, entries[{exercise, sets[{reps, weight_kg, rir?, set_type?}]}], idempotency_key)` лише додає підходи. `update_set(set_id, patch)` виправляє один підхід. `remove_set(set_id)` видаляє з підтвердженням (`destructiveHint: true`). Повторний виклик з тим самим ключем не дублює дані ([MCP: tool annotations](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)).
4. **Опис для тренера в MCP:** «rir 5 means 5 or more; null means not rated; rir_source=prefill means the user did not change the suggestion».
5. **UI — рядок чипів** на екрані таймера відпочинку (або в рядку підходу):

   | Елемент | Текст |
   |---|---|
   | Заголовок | **RIR — скільки ще повторів зміг би?** |
   | Чипи | `0 · 1 · 2 · 3 · 4 · 5+`, кожен 48 px (6 × 48 + 5 × 8 = 328 px — рівно на екран 360 px) |
   | Підпис під вибраним | 0 «Відмова — жодного чистого повтору більше» · 1 «Ще один, і все» · 2 «Ще два» · 3 «Ще три» · 4 «Ще чотири» · 5+ «Легко, запас великий» |
   | Ціль | Контурний чип: «Ціль: 1–2» |
   | Іконка (i) | «RIR — скільки повторів ти ще зробив би з чистою технікою. 0 = відмова. Оцінюй одразу після підходу.» |
   | Тип підходу | «Розминка» / «Робочий» / «Дроп-сет»; для розминки чипи RIR приховані |

   Стани: порожній (допустимо) → заповнено наперед (контур, світлий фон) → підтверджено дотиком (суцільна заливка). Доступність: `role="radiogroup"` і навігація стрілками.
6. **Калібрування (опційно):** раз на 2–4 тижні на останньому підході безпечної ізоляції застосунок пропонує: «Перевірка RIR: передбач запас, потім дотисни до відмови».

**Готово, коли:** у кожного робочого підходу можна поставити RIR одним дотиком; тренер у `get_workout` бачить `[reps, rir]` і `rir_source`; повторний `log_sets` з тим самим ключем нічого не дублює.

## 2. Фільтр за датами й компактний формат історії

**Мета.** Тренер читає історію за будь-який період в одному виклику, не впираючись у ліміт.

**Чому це критично.** 160 КБ на 20 тренувань — це ~40 тис. токенів. Claude Code попереджає вже з 10 тис. токенів і обрізає відповідь MCP на 25 тис. ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)), тож `list_recent_workouts` у нинішньому вигляді тренер фактично не може прочитати. Причина — повний об'єкт вправи, вкладений у кожну вправу кожного тренування. Hevy, для порівняння, зберігає в тренуванні лише id шаблону й назву і віддає максимум 10 тренувань на сторінку.

**Кроки.**

1. **API:** `GET /api/workouts?from&to&status=completed&view=summary|compact|full&limit=20&cursor=…`. `from` і `to` — дати в часовому поясі користувача, обидві включно. Пагінацію курсором закласти одразу: додати її пізніше означає зламати сумісність ([Google AIP-158](https://google.aip.dev/158)).
2. **`view=compact`:** підходи як пари `[reps, rir]`, а словник вправ — один раз на всю відповідь:
   ```json
   {
     "data": [
       { "date": "2026-10-21", "program": "Б", "status": "completed", "durationMin": 67,
         "ex": [ { "e": 12, "w": 20, "sets": [[9,2],[9,1],[8,1],[8,0]] } ] } ],
     "exercises": { "12": { "name": "Присідання", "muscles": {"quads":1,"glutes":0.5} } },
     "setFormat": ["reps","rir"],
     "nextCursor": "eyJ…"
   }
   ```
3. **`view=summary`:** лише агрегати рівня тренування (дата, тривалість, кількість робочих підходів, топ-підхід кожної вправи). 20 тренувань — до ~10 КБ.
4. **MCP:** `list_recent_workouts(from, to, limit, cursor, response_format='concise'|'detailed')`, за замовчуванням concise. Запобіжник на сервері: якщо відповідь перевищує ~20 тис. символів — автоматично concise, `"truncated": true` і підказка «Звузь діапазон або передай cursor» ([Anthropic: writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).
5. **MCP — зведений інструмент `get_training_summary(from, to)`**, базова версія: діапазон, по одному текстовому рядку на сесію (`"2026-10-21 Б 67хв | Присідання 4×9/9/8/8 @20 RIR 2/1/1/0 | …"`), список прапорців. У пунктах 5–7 він розшириться обсягом, дотриманням плану й пропусками.
6. **UI історії:** фільтр «7 днів · 30 днів · 3 місяці · Період…» (за замовчуванням 30 днів), рядок підсумку «12 тренувань · 186 робочих підходів · 14,2 год», кнопка «Показати ще» замість нескінченного прокручування, порожній стан «За цей період тренувань немає» з кнопкою «Розширити до 3 місяців».

**Готово, коли:** історія за 4 тижні у `view=summary` займає до 10 КБ; `get_training_summary` за 4 тижні — до ~1,5 тис. токенів; тренер аналізує 2 тижні одним викликом без читання файлу.

## 3. Розмітка вправ за м'язами

**Мета.** Можна порахувати обсяг на кожен м'яз (пункт 5).

**Кроки.**

1. **Довідник із 17 груп** — таблиця, а не enum, щоб додавати групи без міграції типу. Основа — free-exercise-db, але з розділеною дельтою, бо жоден відкритий набір її не ділить:

   | `code` | Назва | `code` | Назва |
   |---|---|---|---|
   | `chest` | Груди | `forearms` | Передпліччя |
   | `front_delts` | Передня дельта | `abs` | Прес |
   | `side_delts` | Середня дельта | `lower_back` | Поперек |
   | `rear_delts` | Задня дельта | `glutes` | Сідниці |
   | `lats` | Найширші | `quads` | Квадрицепс |
   | `upper_back` | Середина спини | `hamstrings` | Біцепс стегна |
   | `traps` | Трапеція | `adductors` | Привідні |
   | `biceps` | Біцепс | `calves` | Литки |
   | `triceps` | Трицепс | | |

2. **Зв'язок вправи з м'язом:**
   ```sql
   CREATE TABLE exercise_muscle (
     exercise_id     uuid REFERENCES exercise(id) ON DELETE CASCADE,
     muscle_group_id smallint REFERENCES muscle_group(id),
     role            text NOT NULL CHECK (role IN ('primary','secondary')),
     weight          numeric(3,2) NOT NULL DEFAULT 1.0 CHECK (weight > 0 AND weight <= 1),
     PRIMARY KEY (exercise_id, muscle_group_id)
   );
   ```
   Основний = 1, допоміжний = 0,5. Поле `weight` дозволяє винятки, наприклад 0,25 для біцепса в становій тязі.
3. **Стартова розмітка твоїх 14 вправ** — один раз вручну. Приклади: жим лежачи → груди 1, трицепс 0,5, передня дельта 0,5; тяга в нахилі → найширші 1, середина спини 1, біцепс 0,5, задня дельта 0,5; жим стоячи → передня дельта 1, трицепс 0,5, середня дельта 0,5.
4. **API/MCP:** `list_exercises` повертає `muscles: {code: weight}`; новий `set_exercise_muscles(exercise, primary[], secondary[])` — лише з підтвердженням користувача.
5. **UI у формі вправи:** два блоки чипів з множинним вибором, згруповані «Жим · Тяга · Ноги · Корпус»: **«Основні м'язи»** (мінімум один, валідація «Оберіть хоча б один основний м'яз») і **«Допоміжні м'язи · рахуються як ½ підходу»**. Один м'яз не може бути в обох блоках. У каталозі — бейдж **«Без м'язів»** і банер «2 вправи без м'язів — вони не рахуються в тижневому обсязі. Призначити».

**Готово, коли:** у кожної вправи є хоча б один основний м'яз, а `list_exercises` повертає `muscles`.

## 4. Завершення тренування

**Мета.** У статистику й пошук пропусків потрапляють лише справді завершені тренування. Зараз тренування 21.10 досі «відкрите».

Публічного опису автозавершення в Hevy чи Strong немає, тож правило нижче — наше проєктне рішення, і поріг варто тримати в конфігу.

**Кроки.**

1. **БД:**
   ```sql
   ALTER TABLE workout
     ADD COLUMN status text NOT NULL DEFAULT 'completed'
         CHECK (status IN ('in_progress','completed','abandoned')),
     ADD COLUMN end_reason text CHECK (end_reason IN ('manual','auto_idle','auto_next_workout')),
     ADD COLUMN last_activity_at timestamptz,
     ADD COLUMN tz text;  -- 'Europe/Kyiv'
   CREATE UNIQUE INDEX one_open_workout ON workout(user_id) WHERE status = 'in_progress';
   ```
   Частковий унікальний індекс гарантує, що відкритим може бути лише одне тренування.
2. **Разова міграція старих записів:** є `timeEnd` або підходи → `completed`; немає підходів → `abandoned`.
3. **Правило автозавершення** (cron кожні 15–30 хв або «ліниво» при наступному запиті): якщо `in_progress` і від `last_activity_at` минуло понад 3 год → `completed` (є хоча б один робочий підхід) або `abandoned` (підходів немає). Час кінця = `logged_at` останнього підходу + 2 хв, `end_reason = 'auto_idle'`.
4. **Старт нового тренування** закриває відкрите з `end_reason = 'auto_next_workout'`.
5. **Статистика** рахує лише `completed`. Тривалість автозакритих сесій позначається як орієнтовна і не входить у середню.
6. **MCP:** `finish_workout` ідемпотентний — повторний виклик повертає той самий підсумок без помилки.
7. **UI:**
   - Банер на головному екрані: **«Незавершене тренування · 21 жовтня, 10:35 · 18 підходів»** з кнопками «Продовжити» і «Завершити».
   - Діалог при старті нового: «У тебе є незавершене тренування від 21 жовтня. Завершити його і почати нове?» → «Завершити і почати» / «Скасувати».
   - Підсумок при ручному завершенні: тривалість (редагована) і поле «Нотатка до тренування» (див. пункт 7).
   - Бейдж в історії **«Завершено автоматично»** і тривалість зі знаком «≈», підказка: «Тривалість орієнтовна: тренування не завершили вручну. Змінити».

**Готово, коли:** у базі немає «вічно відкритих» тренувань; відкрите буває лише одне; статистика й тренер бачать тільки `completed`.

# B. Дуже бажано

## 5. Тижневий обсяг на м'яз

**Мета.** Тренер одразу бачить «середня дельта — 5 при цілі 12–16», без ручних підрахунків. Потрібен пункт 3.

**Кроки.**

1. **Формула** (дробова: прямий підхід = 1, допоміжний = 0,5). Саме вона найкраще описала дані в метааналізі Pelland 2026 ([SportRxiv](https://sportrxiv.org/index.php/server/preprint/view/460)):
   ```
   sets[muscle][week] = Σ по completed-тренуваннях, по підходах із set_type <> 'warmup'
                        і (rir IS NULL OR rir <= 4):  exercise_muscle.weight
   ```
   Тиждень — ISO (пн–нд) у часовому поясі користувача. `rir <= 4` відсікає «5+» як неробочі підходи.
2. **Цільова смуга** на кожен м'яз з можливістю редагувати: за замовчуванням 12–16, верх 20.
3. **MCP:** розширити `get_training_summary` полем `weekly[].sets[muscle] = {total, direct, indirect, band, status}`, де `status` — `below` / `in_range` / `upper` / `over`. Тренеру повертати і пряму, і непряму складову, бо RP рахує лише прямі підходи ([RP](https://rpstrength.com/training-volume-landmarks-muscle-growth/)).
4. **Серверні прапорці:** «side_delts below band 3 weeks in a row», «понад 10 підходів на м'яз за одну сесію».
5. **UI — екран «Обсяг за тиждень»:** перемикач «‹ 20–26 жовт ›», по рядку на м'яз з bullet chart (фон 0–12 «нижче цілі», 12–16 «ціль», 16–20 «верх діапазону», маркер понад 20; темна смуга — цей тиждень, тонка риска — минулий), сортування «Найбільший дефіцит зверху».

   | Статус | Текст |
   |---|---|
   | < 12 | «Нижче цілі» (нейтральний колір, не червоний) |
   | 12–16 | «У цілі» |
   | 16–20 | «Верх діапазону» |
   | > 20 | «Понад 20 — перевір відновлення» |
   | тиждень не закінчено | «Темп: дійде до ~13 до неділі» |

   Підказка при дотику: «Груди: 13,5 = 10 прямих + 7 × ½ допоміжних. Ціль 12–16». Поруч обов'язково таблиця з тими самими числами — для доступності й для тренера.

**Готово, коли:** `get_training_summary` повертає обсяг на всі 17 груп за кожен тиждень; цифри збігаються з ручним підрахунком на кількох тижнях.

## 6. Плановий графік і пропуски

**Мета.** Тренер знає, що саме мало бути, і не вгадує ритм за вереснем.

Hevy рахує лише тижневий стрік і не вміє планувати майбутні тренування, тож тут MyGym іде далі за лідера. Модель має бути поблажливою: Apple додала паузу кілець, а Duolingo — захист стріку, бо втрата стріку демотивує ([Duolingo Blog](https://blog.duolingo.com/how-streaks-keep-duolingo-learners-committed-to-their-language-goals/)).

**Кроки.**

1. **БД:**
   ```sql
   CREATE TABLE training_schedule (
     id                bigserial PRIMARY KEY,
     user_id           uuid NOT NULL,
     mode              text NOT NULL CHECK (mode IN ('weekdays','frequency')),
     weekdays          smallint[],   -- ISO 1..7, бажані дні
     sessions_per_week smallint,
     rotation          text[],       -- ['А','Б']
     start_date        date NOT NULL,
     tz                text NOT NULL,
     active            boolean NOT NULL DEFAULT true
   );
   ```
2. **Алгоритм** (проєктне рішення):
   - `expected` за тиждень = `sessions_per_week` або кількість бажаних днів, мінус дні оголошеної перерви (пункт 7).
   - Тренування в інший день того самого тижня зараховується замість пропущеного.
   - Поточний тиждень: `at_risk`, коли днів лишилось менше, ніж сесій бракує; `missed` — лише після закриття тижня.
   - Ротація А/Б визначає, яке тренування наступне, але пропуск її не зсуває.
   - Метрики: `adherence_week`, `adherence_4w`, `weekly_streak`, `current_gap_days`.
3. **MCP:** розширити `get_training_summary` блоком `adherence: {planned, completed, missed, longest_gap_days, missed_detail[{date, planned, reason}]}`. Це замінює окремий `get_training_frequency`.
4. **UI:**
   - Налаштування «Розклад»: перемикач «Конкретні дні / N разів на тиждень»; чипи «Пн Вт Ср Чт Пт Сб Нд» з підписом «Дні — орієнтир: тренування в інший день цього тижня теж зарахується»; «Порядок тренувань» з перетягуванням.
   - Картка тижня на головному: «Цього тижня: 2 з 3 · ще одне — і тиждень виконано» і «Сьогодні за планом: А».
   - Календар: виконано (заливка), пропущено (контур, нейтральний колір), звільнено (іконка причини), відпочинок (порожньо).
   - Без докорів: не «Ти пропустив понеділок!», а «2 з 3 цього тижня». Одне нагадування в запланований день: «Сьогодні А. Записати тренування?»

**Готово, коли:** за твоїми даними 8–21.10 сервер сам знаходить пропуски ср 14.10 і пн 19.10 при розкладі пн/ср/пт.

## 7. Причина пропуску й нотатка до тренування

**Мета.** Тренер знає, чому була перерва, бо від цього залежить повернення, а хвороба — окрема гілка безпеки.

**Кроки.**

1. **БД:**
   ```sql
   CREATE TABLE training_break (
     id        bigserial PRIMARY KEY,
     user_id   uuid NOT NULL,
     starts_on date NOT NULL,
     ends_on   date,  -- NULL = триває
     reason    text NOT NULL CHECK (reason IN ('illness','injury','travel','fatigue','busy','other')),
     note      text,
     source    text NOT NULL CHECK (source IN ('prompt','manual','ai_coach'))
   );
   ALTER TABLE workout
     ADD COLUMN note text,
     ADD COLUMN ended_early_reason text
         CHECK (ended_early_reason IN ('time','fatigue','pain','illness','equipment','other'));
   ```
   Пропущені сесії всередині перерви успадковують її причину.
2. **Коли питати:** при першому відкритті після закриття тижня з пропуском або паузи довшої за `max(плановий інтервал + 1 день, 3 дні)`. Про ту саму паузу двічі не питати. Поріг — проєктне рішення.
3. **MCP:** `log_break(starts_on, ends_on?, reason, note?)` — ідемпотентний; причини з'являються в `get_training_summary.adherence.missed_detail`. Причини «Хвороба» і «Біль / травма» вмикають у тренера гілку безпеки.
4. **UI:**
   - Немодальна картка: **«Схоже, перерва з 14 жовтня. Що сталося?»** з чипами «Хвороба · Біль / травма · Поїздка · Втома · Робота / справи · Інше», полем «Коментар (необов'язково)» і кнопкою «Пропустити».
   - Дія в меню «Запланувати перерву»: «До понеділка / До дати…» + причина. Такі тижні не рахуються в дотриманні й не рвуть стрік.
   - Поле «Нотатка» в підсумку тренування з підказкою «Як пройшло? Що варто врахувати наступного разу». За потреби «Чому завершено раніше?» з чипами.

**Готово, коли:** у кожного пропуску в `missed_detail` є причина або явне «не вказано», а нотатки до тренувань видно тренеру.

# C. Пізніше

## 8. Анкета готовності перед тренуванням

**Мета.** Суб'єктивний сигнал стану до появи годинника, а згодом — резерв на дні без даних.

**Кроки.**

1. **БД:**
   ```sql
   CREATE TABLE readiness_check (
     id           bigserial PRIMARY KEY,
     user_id      uuid NOT NULL,
     workout_id   uuid UNIQUE REFERENCES workout(id) ON DELETE SET NULL,
     local_date   date NOT NULL,
     sleep_hours  numeric(3,1),
     sleep_source text CHECK (sleep_source IN ('user','device')),
     wellbeing    smallint CHECK (wellbeing BETWEEN 1 AND 5),   -- 5 = добре
     soreness     smallint CHECK (soreness BETWEEN 1 AND 5),    -- 5 = дуже болить
     illness      text CHECK (illness IN ('none','above_neck','systemic')),
     UNIQUE (user_id, local_date)
   );
   ```
2. **MCP:** `log_readiness(date, …)` — upsert за датою, тому природно ідемпотентний; останні значення — у `get_training_summary.readiness_last`.
3. **UI — нижній аркуш при «Почати тренування»**, кнопка «Пропустити» завжди видна, до 10 секунд на заповнення. Чипи підписані **словами**, а не цифрами: так не плутається напрям шкал (у самопочутті 5 — добре, у болючості 5 — погано).

   | Рядок | Чипи |
   |---|---|
   | **Сон минулої ночі** | «≤5 год · 6 · 7 · 8 · 9+» (з годинника — заповнено, позначка «з годинника») |
   | **Самопочуття** | «Погано · Так собі · Нормально · Добре · Чудово» |
   | **Болючість м'язів** | «Немає · Легка · Помірна · Сильна · Дуже сильна» |
   | **Ознаки хвороби?** | «Ні · Застуда без температури · Температура / ломота» |

   Четвертий рядок додано свідомо: він вмикає правило безпеки. На «Температура / ломота» аркуш показує «Сьогодні краще відпочити. Тренер у чаті підкаже, коли повертатися», але тренування не блокує.

**Готово, коли:** анкету можна заповнити за 10 секунд або пропустити; тренер бачить її відповіді.

## 9. Дані годинника й ваг

**Мета.** Тренер у чаті бачить сон, пульс спокою, HRV і вагу як тренд проти твоєї власної норми.

Google Fit API підтримується лише до кінця 2026 року ([Google Fit Migration FAQ](https://developer.android.com/health-and-fitness/health-connect/migration/fit/faq)). Health Connect зберігає дані на телефоні, тож бекенд отримає їх лише через Android-компаньйон (або мобільний MyGym). Повний опис — у «ТЗ: інтеграція розумних ваг і годинника в MyGym».

**Кроки.**

1. **Компаньйон:** вхід в акаунт MyGym, дозволи лише на читання шести типів (`SleepSession`, `RestingHeartRate`, `HeartRateVariabilityRmssd`, `Weight`, `BodyFat`, `Steps`), плюс `READ_HEALTH_DATA_IN_BACKGROUND` і за бажанням `READ_HEALTH_DATA_HISTORY` (без нього доступні лише 30 днів історії). Фонова синхронізація WorkManager раз на годину, `POST /api/health/ingest`.
2. **Обов'язкові вимоги Google:** екран-пояснення дозволів із політикою конфіденційності; перевірка дозволів перед кожним читанням; після двох відмов поспіль запит більше не показується — тоді вести в налаштування Health Connect; біля кожного значення показувати джерело ([Health Connect permissions](https://developer.android.com/health-and-fitness/health-connect/ui/permissions)).
3. **БД:** таблиця `health_daily` (денні агрегати: сон, медіана нічного пульсу, медіана rMSSD, вага, % жиру, кроки, джерела, час синхронізації).
4. **Готовність — три рівні без бала 0–100**, кожен з поясненням правила. Fitbit критикують саме за бал без відповіді на «чому?».

   | Стан | Текст | Підзаголовок |
   |---|---|---|
   | Зелений | ✓ **«Готовий тренуватися за планом»** | «Сон і пульс спокою в межах твоєї норми» |
   | Жовтий | ◐ **«Тренуйся, але без рекордів»** | «Пульс спокою +3 уд/хв від норми» |
   | Червоний | ◯ **«Сьогодні пріоритет — відновлення»** | «Пульс спокою +4 уд/хв дві ночі поспіль» |
   | Калібрування | «Вивчаємо твою норму: 4 з 14 ночей» | — |
   | Неповні дані | «На основі 2 з 3 сигналів» | «Сну за минулу ніч немає» |

   Внизу дрібно: «Не є медичною порадою». Слів «небезпека», «аномалія» в текстах немає.
5. **MCP:** `get_readiness(from, to)` під окремим дозволом `health:read`, повертає денні агрегати з відхиленням від норми, джерелом і правилом, що спрацювало.
6. **UI у MyGym-вебі:** окремий дашборд не потрібен. Досить рядка статусу на аркуші анкети (пункт 8), який сам підставляє сон.

**Готово, коли:** уранці тренер через `get_readiness` бачить статус за минулу ніч з правилом і джерелом; без годинника працює анкета.

## 10. Біль і травми

**Мета.** Тренер застосовує правило болю, а не здогадується, чому впала вага, як із жимом лежачи 7.10.

**Кроки.**

1. **БД — стійкий прапорець, а не нотатка:**
   ```sql
   CREATE TABLE pain_report (
     id                  bigserial PRIMARY KEY,
     user_id             uuid NOT NULL,
     workout_exercise_id uuid REFERENCES workout_exercise(id) ON DELETE SET NULL,
     exercise_id         uuid REFERENCES exercise(id),
     site     text NOT NULL,  -- shoulder, elbow, wrist, lower_back, knee, hip, other
     side     text CHECK (side IN ('left','right','both')),
     score    smallint NOT NULL CHECK (score BETWEEN 0 AND 10),
     timing   text CHECK (timing IN ('during','after','both')),
     sharp    boolean NOT NULL DEFAULT false,
     note     text,
     status   text NOT NULL DEFAULT 'active' CHECK (status IN ('active','resolved')),
     reported_at timestamptz NOT NULL DEFAULT now(),
     resolved_at timestamptz
   );
   ```
2. **MCP:** `report_pain(...)` і `resolve_pain(pain_id)`; активні скарги — у `get_training_summary.active_pain` і серверні прапорці «3 скарги на плече за 14 днів».
3. **UI:** іконка **«Біль»** на картці вправи відкриває аркуш «Де болить?» з чипами місця (першими — суглоби, пов'язані з цією вправою: «Плече · Лікоть · Зап'ястя · Поперек · Коліно · Кульшовий · Інше»), сторона «Ліва · Права · Обидві», шкала «Наскільки сильно? 0–10» у два рядки чипів з підписами «0 — немає» і «10 — нестерпно», «Під час повторів · Після · Весь час», перемикач «Різкий / раптовий біль», поле «Нотатка».
4. **Реакція застосунку** (градуйоване правило болю та червоні прапорці NHS Scotland, [NHS](https://rightdecisions.scot.nhs.uk/dg-refhelp/musculoskeletal-system/shoulder/)):

   | Умова | Повідомлення |
   |---|---|
   | 1–3 | «Записано. Вагу на цій вправі наступного разу не підвищуємо.» |
   | 4–6 | «Зменш вагу або заміни вправу. Тренер у чаті запропонує заміну.» |
   | ≥7 або різкий | «Зупини цю вправу. Якщо біль різкий, є слабкість чи клацання — звернися до лікаря.» |

5. **Наступного разу** на тій самій вправі — банер **«Минулого разу: ліве плече 4/10. Як зараз?»** з чипами «Не болить» (закриває прапорець), «Так само», «Гірше». У профілі — розділ «Активні скарги».

**Готово, коли:** скаргу можна поставити за 3–4 дотики; вона висить, доки її не закрили; тренер бачить її в `active_pain`.

# Зведення: MCP-інструменти після всіх пунктів

| Інструмент | З'являється в пункті | Роль |
|---|---|---|
| `get_training_summary(from, to)` | 2, розширюється в 5, 6, 7, 8, 10 | Головний інструмент читання: сесії, обсяг, дотримання, пропуски, біль, прапорці |
| `list_recent_workouts(from, to, cursor, response_format)` | 2 | Історія, за замовчуванням стисла |
| `get_workout`, `get_exercise_history` | без змін | Деталі сесії та прогрес вправи |
| `log_sets`, `update_set`, `remove_set` | 1 | Безпечний запис замість `log_workout_exercises` |
| `finish_workout` | 4 | Ідемпотентне завершення |
| `set_exercise_muscles` | 3 | Розмітка м'язів (з підтвердженням) |
| `log_break` | 7 | Перерва та її причина |
| `log_readiness` | 8 | Анкета, upsert за датою |
| `get_readiness` | 9 | Дані годинника й ваг, окремий дозвіл `health:read` |
| `report_pain`, `resolve_pain` | 10 | Скарги на біль |

У інструкціях сервера першим рядком: «Для питань про тренування, прогрес, обсяг, пропуски й готовність почни з `get_training_summary`; `get_workout` викликай лише для деталей конкретної сесії».

Пороги, які конкуренти не публікують, — це проєктні рішення: автозакриття через 3 год, коли питати про перерву, алгоритм пропусків, смуга 12–16/20. Тримай їх у конфігу й підлаштовуй під свої дані. Найсильніше обґрунтовані якраз ті рішення, що змінюють твою ідею: нуль і «5+» на шкалі RIR, дробовий підрахунок 0,5 і статус готовності за пояснюваними правилами замість бала.
