Ціль: `$ARGUMENTS`

Проведи повний робочий цикл над цією ціллю в MyGym.

## 1. Розуміння

- Перефразуй ціль у одному реченні. Якщо трактується неоднозначно — постав ОДНЕ
  уточнююче питання й зупинись (`AskUserQuestion`, якщо вибір справді користувацький).
- Зберемо базовий контекст: `git status`, чи піднятий dev-стек
  (`docker compose -f docker-compose.dev.yml ps`), релевантні файли з `CLAUDE.md`.

## 2. План

- Для нетривіальних цілей (3+ кроки, кілька файлів/шарів backend+frontend) —
  явно зафіксуй план (за потреби через `EnterPlanMode` або `Task(subagent_type=Plan, ...)`
  для архітектурних рішень). Не плануй «подумки» — явний план дає видимість.
- Занеси кожен крок через `TaskCreate`, якщо кроків 3+ — це зберігає прогрес між кроками.

## 3. Делегування

Для кожного кроку — обери відповідний інструмент:

- Потрібне дослідження незнайомої ділянки коду чи зовнішньої бібліотеки →
  `Task(subagent_type=researcher, ...)` (або `Explore` для швидкого пошуку файлу/символу).
- Реалізація коду (backend, frontend, Docker/конфіг) — роби **сам, у головній сесії**:
  MyGym соло-проєкт, окремий агент-«implementer» тут зайвий шар делегування.
- Незалежні дослідницькі `Task`-и запускай в одному повідомленні для паралелізації.

Після кожного `Task` — онови статус через `TaskUpdate`.

## 4. Перевірка

- Для нетривіальних чи ризикованих змін (auth, схема БД, платні/незворотні дії) —
  виклич `Task(subagent_type=reviewer, ...)` за другою думкою.
- Якщо змінилась логіка, яку можна перевірити (backend-роут, progression-правило,
  CSV-парсинг) — виклич `Task(subagent_type=tester, ...)`: автотестів у проєкті поки
  немає, тож tester валідує через реальний docker-стек (curl, docker compose logs).
- Знайдено BLOCKER у рев'ю — повернись до кроку 2 з оновленим контекстом, не приховуй проблему.

## 5. Звіт користувачу

```
## Зроблено
- <крок 1>: <короткий результат>
- <крок 2>: ...

## Не зроблено / відкладено
- <причина, якщо є>

## Наступний крок
<рекомендація: показати дифф / закомітити / обговорити>
```

- Якщо торкнулись backend-схеми, progression-правил, CSV-імпорту, Docker/dev-нюансів
  чи стеку — запропонуй наприкінці `/update-context`, щоб точково оновити відповідні
  секції `CLAUDE.md` (сам не запускай без підтвердження, якщо зміни не тривіальні).

## Залізні правила

- **Не приховуй невдач.** Якщо щось пішло не так — це чесно перший пункт звіту.
- **Не дублюй роботу між агентами.** Якщо `researcher` уже знайшов файл — передай це
  напряму в реалізацію, не змушуй шукати знову.
- **Жодних незворотних дій** (force-push, `rm -rf`, `docker compose down -v`, DROP)
  без явної згоди користувача — це вже покриває загальний Git Safety Protocol сесії.
- Коміти — тільки якщо користувач явно попросив (як завжди в цій сесії).
