Інкрементально оновлює кореневий `CLAUDE.md` і правила `.claude/rules/*.md`: читає реальні зміни коду →
править лише зачеплені секції. Не переписує файл цілком і не займається
косметикою — лише факти, яких торкнулася ця дельта.

Аргумент `$ARGUMENTS` — `since:<ref>` (база diff). Без нього: `git diff HEAD` +
`git diff --cached` (незакомічене) або, якщо чисто, `git diff HEAD~1..HEAD`.

## Крок 1 — Зібрати дельту

```bash
git status --porcelain
git diff HEAD -- backend/ frontend/ docker-compose*.yml
```

Якщо дельти нема — сказати «CLAUDE.md актуальний» і вийти.

## Крок 2 — Зіставити змінені шляхи ↔ документи

Документація розкладена на кореневий `CLAUDE.md` (спільне для кожної сесії) і правила
`.claude/rules/<тема>.md` (деталі модулів, вантажаться за `paths:`).

- Змінений файл підпадає під `paths:` якогось правила (`grep -l` по frontmatter
  `.claude/rules/*.md`) → правиш це правило. Під кілька — те, де про поведінку шукатимуть.
- Не підпадає під жодне: `backend/src/db/schema.ts` → `## Модель даних`; залежності стеку
  (`*/package.json`) → `## Стек`; патерн `frontend/src/shared/api/**` → `## Стек`; захист API,
  тести, CI → `## Захист API та тести`; i18n-конвенції → `## Локалізація` — усе в `CLAUDE.md`.
- Нова тема (новий модуль) → нове правило з `paths:` + рядок у таблиці «Де що описано»
  `CLAUDE.md`. Новий файл наявної теми поза її `paths:` → допиши glob.
- `git-workflow.md` не чіпати — це процес, а не документація.

Документів, яких зміни не торкнулися, — не чіпати.

## Крок 3 — Оновити лише зачеплені секції через Edit

Для кожної зачепленої секції:
- прочитай реальний змінений код (не тільки diff-контекст наосліп) — нові поля,
  правила, ендпоінти;
- внеси точкову правку у відповідний документ через `Edit` (не `Write` всього файлу);
- пиши українською, у стилі решти файлу (стисло, конкретно, без вступів);
- лише підтверджене з коду; невідоме — не вигадуй, або познач одним словом
  проблему, яку варто уточнити в користувача;
- значні технічні рішення чи gotchas — у стилі вже наявних приміток
  («Windows-специфічні нюанси» — приклад формату: коротко проблема → коротко фікс).

## Крок 4 — Підсумок

```
Оновлено:
- <файл> → <секція> ← <файли, що спричинили правку>
- ...
```

Якщо торкнулась `## Стан проєкту`, а сама фіча ще не перевірена наживо (dev-стек,
curl, UI) — не пиши "перевірено", напиши, що саме лишилось перевірити.

## Правила

- **Інкрементально:** тільки секції, яких торкнулися зміни. Без повної регенерації.
- **Anti-hallucination:** лише факти з коду; невідоме не вигадувати.
- Це не заміна ручного рев'ю — після виклику коротко покажи користувачу, що саме
  змінилось у документах (diff), а не просто скажи "оновив".
