Задача: `$ARGUMENTS`

Проведи цикл **план → реалізація → рев'ю → тести → документація**. Git-правила —
`.claude/rules/git-workflow.md`, контекст проєкту — `CLAUDE.md`.

## 0. Підготовка гілки

1. `git status` і `git branch --show-current`.
2. Якщо на `main` є незакомічені зміни, що не стосуються задачі — **зупинись і спитай**,
   що з ними робити (не стешити й не комітити їх самому).
3. Визнач тип (`feat` / `fix` / `chore` / `refactor`) і коротку назву → створи гілку
   від `main`: `git switch -c feat/<назва>`. Якщо вже на відповідній feature-гілці — продовжуй у ній.

## 1. План — потім СТОП

1. Перефразуй задачу одним реченням. Неоднозначно → одне уточнююче питання.
2. Досліди зачеплений код: `Explore` для швидкого пошуку, `researcher` — якщо треба
   зрозуміти незнайому ділянку або зовнішню бібліотеку (незалежні дослідження — паралельно, в одному повідомленні).
3. Склади план:
   ```
   ## Ціль
   ## Що змінюється
   - db: <таблиці/поля + міграція>          (якщо є)
   - backend: <модулі, ендпоінти, Zod-схеми>
   - frontend: <сторінки, компоненти, api/hooks, i18n-ключі en+uk>
   ## Кроки = майбутні коміти
   1. feat(db): ...
   2. feat(backend): ...
   ## Як перевіримо
   - backend-тести: <які нові/змінені>
   - вручну: <сценарій у dev-стеку>
   ## Ризики / відкриті питання
   ```
4. Занеси кроки через `TaskCreate`.
5. **Зупинись і дочекайся підтвердження плану.** Не редагуй код до "ок".
   Виняток: тривіальна правка (1 файл, очевидна) — тоді план одним рядком і одразу далі.

## 2. Реалізація

- Роби сам, у головній сесії (окремий implementer для соло-проєкту — зайвий шар).
- Дотримуйся конвенцій із `CLAUDE.md`: Fastify + Zod, Drizzle (транзакції — `tx`, не `db`),
  TanStack Query у `frontend/src/shared/api/<ресурс>/`, i18n-ключі одночасно в `en.json` і `uk.json`.
- Нова backend-логіка → тест у `backend/test/` у межах цієї ж задачі.
- Після кожного завершеного кроку плану: `npm run typecheck` (backend) / `npm run build`
  (frontend, якщо чіпали) → коміт за Conventional Commits → `TaskUpdate`.
- Відхилився від плану — скажи про це користувачу, не мовчки.

## 3. Рев'ю

`Task(subagent_type=reviewer)` з брифом: мета задачі + "переглянь `git diff main...HEAD`,
читай змінені файли повністю".
- BLOCKER / MAJOR → виправ → окремий `fix:`-коміт → за потреби повторне рев'ю.
- MINOR → виправ, якщо дешево; інакше — у звіт.

## 4. Тести

`Task(subagent_type=tester)` з брифом: що змінилось і що перевірити. Мінімум:
- `cd backend && npm run typecheck && npm test`
- `cd frontend && npm run build`
- однакові набори ключів у `frontend/src/i18n/locales/en.json` і `uk.json`
- ручний сценарій у dev-стеку (curl до `/api/...` або опис кроків у UI), якщо змінилась поведінка.

Падіння → виправ → `fix:`-коміт → повтори. Тести не глушити й не послаблювати.

## 5. Документація

Лише після зелених рев'ю й тестів — щоб документувати остаточний код.

`Task(subagent_type=docs-keeper)` з брифом: мета задачі + "онови живу документацію
(`CLAUDE.md`, `docs/db/`) під усе, що змінилось від `docs/.docs-synced` — поточний стан,
без історії". Базу він визначає сам, тож підхопить і зміни, зроблені поза `/feature`.
- Перевір `git diff -- CLAUDE.md docs/` (вигадане чи зайве — прибери) →
  коміт `docs: <що оновлено>` (або `docs(db): …`, якщо лише схема) разом із `docs/.docs-synced`.
- `NO_DOC_CHANGES` → коміт лише `docs/.docs-synced`: `docs: mark docs synced`.
- У звіті docs-keeper є коміти «поза оркестратором» → покажи їх користувачу.
- «Схему не перезнято» → застосуй міграції в dev-стеку (`npm run db:migrate`, з
  підтвердженням) і запусти `docs-keeper` ще раз.
- «Поза документами» → у звіт, сам не виправляй мовчки.
- Код змінився після цього кроку (правки користувача, повторне рев'ю) → повтори крок.

## 6. Звіт

```
## Гілка
feat/<назва> — N комітів

## Зроблено
- <коміт/крок>: <результат>

## Перевірено
- тести: PASS (X) / вручну: <що>
- рев'ю: <вердикт, що виправлено>

## Документація
- <що оновив docs-keeper> | NO_DOC_CHANGES

## Не зроблено / ризики

## Далі
git push -u origin feat/<назва>  → PR у main (CI → після merge автодеплой)
```

- `/update-context` — лише для змін поза `/feature`; у циклі документацію вже оновив крок 5.
- **Не пуш і не мерж сам** — це робить користувач (або ти після явного "запуш").
